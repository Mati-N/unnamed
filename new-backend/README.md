# Node.js Backend Refactor (KeystoneJS)

This project is a refactor of a Django-based backend to Node.js using KeystoneJS 6.
It aims to replicate the core functionalities of the original application, including user authentication, social features (posts, comments, likes, follows), notifications, and a CMS component (migrating from Wagtail to KeystoneJS).

## Current Status (Phases 1-4 - Conceptual Completion)

The following core features and planning documents have been implemented/created:

*   **Project Setup:** Node.js project with TypeScript, Prisma (PostgreSQL), ESLint, Prettier.
*   **Core Data Models:** Schemas for User, Post, Comment, Like, Following, Notification, Page defined in `prisma/schema.prisma` and Keystone lists in `src/schema.ts`.
*   **User Authentication:** JWT-based stateless sessions.
*   **Social Features:** Access controls, virtual fields (`isFollowing`, `liked`, count fields), automatic user association for created content, sortable `likeCount`.
*   **Notification System:** Automatic creation on events, `readNotification` mutation, basic real-time subscription setup.
*   **File Uploads (Profile Images):** Integrated with Cloudinary.
*   **CMS Content Modelling:** Basic `Page` list with a `document` field and example `componentBlocks` (Image, CallToAction, Quote) to replicate Wagtail's StreamField flexibility.
*   **Documentation:**
    *   This README.
    *   `instructions.txt`: For local setup.
    *   `docs/migration-strategy.md`: Conceptual plan for Wagtail to KeystoneJS data migration and verification.
    *   `docs/api-testing-plan.md`: Conceptual plan for API testing.
    *   `docs/deployment-considerations.md`: Includes Dockerfile info, Procfile info, production environment setup, and conceptual deployment/monitoring steps.

## CMS Configuration and Content Modelling (KeystoneJS)

KeystoneJS serves as both the backend API engine and the Headless CMS.

*   **Admin UI:** The CMS administrative interface is automatically generated by KeystoneJS based on your schema. It's typically accessible at `http://localhost:3000` when running the development server. Access is controlled by the `isAccessAllowed` setting in `src/keystone.ts`.
*   **Main Configuration:** The core KeystoneJS setup, including database connection, session management, and enabling the Admin UI, is configured in `src/keystone.ts`.
*   **Content Types (Lists):** All content types, including those for the CMS (like the `Page` list) and user-generated content (like `Post`, `Comment`), are defined as "lists" in `src/schema.ts`.
*   **Flexible Page Content:** The `Page` list uses Keystone's `document` field for its `content`. This field allows for rich text formatting and, critically, the embedding of custom `componentBlocks` (defined in `src/schema.ts` within the `PageListConfig`). These component blocks are designed to replicate the functionality of Wagtail's StreamField blocks, allowing for flexible and structured page content (e.g., image galleries, CTAs, quote blocks).
*   **Data Migration from Wagtail:** A conceptual strategy for migrating content from Wagtail (including StreamField data to Keystone document fields) is outlined in `docs/migration-strategy.md`.

## Setup Instructions (Local Development)

1.  **Clone the repository / Ensure you are in the `new-backend` directory.**

2.  **Install Dependencies:**
    ```bash
    npm install
    # or
    yarn install
    ```

3.  **Configure Environment Variables:**
    *   Copy the `.env.example` (if provided) or create a `.env` file in the `new-backend` root.
    *   Update the following variables in `.env`:
        ```env
        DATABASE_URL="postgresql://YOUR_DB_USER:YOUR_DB_PASSWORD@YOUR_DB_HOST:YOUR_DB_PORT/YOUR_DB_NAME" # Replace with your PostgreSQL connection string
        SESSION_SECRET="your-super-strong-and-long-session-secret" # Replace with a strong secret

        # Cloudinary Credentials (if not already set for a different project part)
        CLOUDINARY_CLOUD_NAME="your_cloudinary_cloud_name"
        CLOUDINARY_API_KEY="your_cloudinary_api_key"
        CLOUDINARY_API_SECRET="your_cloudinary_api_secret"

        # Optional:
        # PORT=3000 # Default port Keystone will try to use
        ```

4.  **Database Migration:**
    *   Apply database migrations to create the tables based on `prisma/schema.prisma`.
    *   KeystoneJS uses Prisma Migrate.
    ```bash
    npx prisma migrate dev --name initial_schema
    # Or if you already have migrations and want to deploy:
    # npx prisma migrate deploy
    ```
    *   This will also generate the Prisma Client.

5.  **Generate KeystoneJS Types (Important for TypeScript):**
    *   This step is crucial for TypeScript to correctly type Keystone's context, lists, etc.
    ```bash
    npx keystone postinstall --fix
    # or simply 'npx keystone postinstall'
    ```
    *   *Note: This step has been problematic in the current automated execution environment but is essential for local development.*

6.  **Build the Project (if you made changes to TypeScript):**
    ```bash
    npm run build
    # (Assuming a build script like "tsc" or "keystone build" is in package.json)
    # For Keystone 6, 'keystone build' is typical for a production build.
    # For development, 'keystone dev' often handles this.
    ```
    Keystone's `keystone dev` usually handles TypeScript compilation on the fly. A specific build step might be `npx keystone build --no-ui` if you only want to build the API.

7.  **Run the Development Server:**
    ```bash
    npm run dev
    # (Assuming a dev script like "keystone dev" is in package.json)
    ```
    This will typically start the KeystoneJS server, and you can access:
    *   **GraphQL API:** Usually at `http://localhost:3000/api/graphql`
    *   **Admin UI:** Usually at `http://localhost:3000`

## Known Issues in Automated Development Environment

*   **Keystone Type Generation:** The `npx keystone postinstall --fix` command, which generates crucial TypeScript definitions (`.keystone/types.ts`), has consistently failed in the automated development environment used for generating this codebase. This is likely due to an `esbuild` or path resolution issue within the tool's sandboxed execution. This means that while the code logic has been implemented, compile-time TypeScript checking for Keystone-specific types was not fully active during generation. This step is **critical** for a proper local development setup.
